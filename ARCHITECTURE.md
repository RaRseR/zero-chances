Версия: 3.1 · Дата: 2026-08-27 · Godot 4.6, C# (net8.0)
Статус: **согласовано с Русланом**, к реализации.

Смежный документ: `claude/rune-pixel-perfect-plan.md` (рендер-пайплайн, пиксель-перфект, LOD).

> **v3.0 — один проект.** Отдельные сборки `Core`, `Server` и `Tests` убраны: для соло-проекта
> это был налог, а не польза. Всё живёт в `rune.csproj` плоскими папками, сетевая логика уходит
> в автолоады. Граница между симуляцией и движком остаётся, но держится соглашением, а не
> компилятором. Разбор — §2, §3, §13.

## 0. Зафиксированные решения

| Вопрос | Решение | Следствие |
|---|---|---|
| Игровая сетка | **Тайлы поверх точек высот**. 1 тайл = `TILE_POINTS × TILE_POINTS` точек (старт: 10×10 = 1000×1000 мировых единиц) | Рельеф остаётся плотным для визуала и разрушений; геймплей живёт на разреженной сетке |
| Модель хода | **Одновременное планирование + фаза разрешения** | Время круга не зависит от числа игроков; резолвер конфликтов живёт на сервере |
| Сетевая модель | **Listen-server: один игрок хостит матч, остальные подключаются через Steam** | Хостинг не нужен вообще. Хост — источник правды для всех |
| Случайность | **Только на хосте** | Остальные пятнадцать игроков не могут подсмотреть пак, колоду или чужие войска |
| Форма сервера | **Обычные C#-классы внутри процесса хоста, на отдельном потоке; владеет ими автолоад** | Отдельной сборки нет — граница держится соглашением, а не компилятором |
| Карта мира | Хост стримит карту. **Для Large/Huge открыт вопрос гибрида** (§4.2) | Аплинк хоста — домашний, а не датацентровый. На больших мирах это решает |
| Транспорт | **Steam P2P через Steamworks.NET**; сейчас `LocalTransport` | Steam даёт identity, лобби, приглашения и NAT traversal бесплатно |
| Порядок реализации | **Сейчас — сервер in-process, сокеты потом** | Вся логика сразу правильная; бонусом рабочий офлайн-режим |
| Мобильный экспорт | Не планируется | Условных TFM для android/iOS нигде нет |
| Приоритеты | Генерация мира (теги → STEP) → команды и стартовые города → карты → визуал | |

Принцип, из которого следует всё остальное: **симуляция не знает про Godot**. Он нужен, чтобы
логику можно было гонять на отдельном потоке и когда-нибудь вынести в выделенный сервер.
С отказом от отдельной сборки принцип не изменился, но перестал проверяться компилятором —
теперь это дисциплина, а не гарантия.

## 1. Топология

```
		МАШИНА ХОСТА (один процесс)
┌───────────────────────────────────────────────┐
│  ┌─────────────────────────────────────────┐  │
│  │ КЛИЕНТ (Godot, главный поток)           │  │
│  │ рендер, ввод, UI, локальная копия мира  │  │
│  └──────────────────▲──────────────────────┘  │
│                     │ LocalTransport          │      Steam P2P (SDR)
│  ┌──────────────────▼──────────────────────┐  │   ┌──────────────────────┐
│  │ MATCHHOST (отдельный поток, без Godot)  │◀─┼──▶│ КЛИЕНТ 2 (Godot)     │
│  │                                         │  │   └──────────────────────┘
│  │ MatchState — единственная правда        │  │   ┌──────────────────────┐
│  │ Rng        — единственный источник      │◀─┼──▶│ КЛИЕНТ 3 …           │
│  │              случайности                │  │   └──────────────────────┘
│  │ TurnController, CommandResolver         │  │            … до 16
│  │ генерация мира, раздача паков           │  │
│  │ фильтрация по туману войны              │  │
│  └─────────────────────────────────────────┘  │
└───────────────────────────────────────────────┘
```

Клиент — средство отображения и ввода. Он держит копию состояния, чтобы рисовать картинку,
но копия **производная**: любое расхождение разрешается в пользу хоста. Клиент не бросает
кубики, не решает исходы боёв и не знает, что лежит в невскрытом паке.

Хост при этом остаётся обычным клиентом со своей копией состояния. Он не читает `MatchState`
напрямую и общается с ним через тот же `ITransport`, что и все остальные, — просто у него
транспорт локальный. Иначе на хосте и на остальных пошли бы разные пути кода, и половина
багов вылезала бы только у гостей.

**`MatchHost` обязан жить на своём потоке.** Генерация Huge-мира — это секунды работы;
на главном потоке Godot она превратится в замерший экран. Поэтому `LocalTransport` — не
прямой вызов, а пара потокобезопасных очередей. Ровно та же семантика, что у сетевого
транспорта: отправил сообщение, ответ придёт позже.

Владеет `MatchHost` автолоад `Match`, а сетью занимается автолоад `Network`. Оба — тонкие
прослойки: держат обычные классы и передают им сообщения, но логики не содержат.

Сейчас сети нет вовсе: локальный транспорт, один игрок, всё в одном процессе. Это уже рабочий
офлайн-режим, и он останется рабочим навсегда.

## 2. Схема слоёв

```
┌──────────────────────────────────────────────────────────────┐
│  СЦЕНЫ И УЗЛЫ                                                 │
│  UI (меню, HUD, рука карт) · World/View (террейн, вода)      │
│  Camera (пиксель-снаппинг, зум, LOD)                          │
└───────────────┬──────────────────────────────▲───────────────┘
				│ Command (намерение)          │ события
┌───────────────▼──────────────────────────────┴───────────────┐
│  АВТОЛОАДЫ                                                    │
│  SteamManager — Steam, лобби, P2P-пакеты                      │
│  Match   — у хоста владеет MatchHost; у всех — копия состояния│
└───────────────┬──────────────────────────────────────────────┘
				│ владеет
┌───────────────▼──────────────────────────────────────────────┐
│  СИМУЛЯЦИЯ — обычные C#-классы, без Godot                     │
│  MatchHost, TurnController, CommandResolver                   │
│  Generation (теги → Planner → Step[]), Grid, Rand             │
└──────────────────────────────────────────────────────────────┘
```

Правило осталось прежним: **симуляция не знает про Godot.** Раньше его гарантировал компилятор —
`using Godot;` в `Core` не собирался. Теперь это соглашение, и держать его придётся самим.

Соглашение не формальность. От него зависят две вещи: логику можно гонять на отдельном потоке
(генерация Huge-мира — секунды работы, на главном потоке это замерший экран), и её можно
когда-нибудь вынести в выделенный сервер, не переписывая.

Автолоад — тонкая прослойка. Он владеет обычными классами и передаёт им сообщения, но сам
логики не содержит. Как только в `_Process` автолоада появится расчёт хода, оба свойства выше
потеряются молча.

## 3. Структура папок

Один проект, плоские папки в корне, без вложенных сборок.

```
rune/
├─ Assets/           шейдеры, текстуры, модели
├─ Autoloads/        SteamManager, дальше Network и Match
├─ Camera/           Camera.cs — ортокамера, пиксель-снаппинг, ступени зума
├─ Card/             карты: определения, редкости, колода, паки, эффекты
├─ Features/         теги мира по категориям
│  ├─ WorldFeature.cs
│  ├─ SizeFeatures.cs
│  └─ ShapeFeature.cs        (остальные семь категорий — по мере надобности)
├─ UI/
│  ├─ Menu/
│  │  ├─ MenuRoot.cs / .tscn  переключатель страниц и стек возврата
│  │  └─ Pages/
│  │     ├─ Main/             MainPage.cs / .tscn
│  │     ├─ Play/             PlayPage.cs / .tscn
│  │     └─ Bots/             BotsPage.cs / .tscn
│  ├─ Settings/      SettingsPage.cs / .tscn
│  └─ Pause/         PausePage.cs / .tscn
├─ Session/          SessionConfiguration — параметры матча, из них строится мир
├─ Utils/            Rand и дальше хеши, математика, расширения
├─ World/            Grid, World.cs (рендер), Generator/
├─ project.godot
├─ rune.csproj
└─ rune.sln
```

Namespace нет нигде — проект один, всё в глобальном пространстве имён. Это осознанно:
namespace был нужен, чтобы развести сборки, а теперь только добавлял бы `using`-и.

Каждая страница — самостоятельная сцена с собственным скриптом. Общих базовых классов нет:
`MenuRoot` только подменяет сцены и ведёт стек возврата, а страница знает лишь пути к своим
соседям. Связь снизу вверх — через `MenuRoot.FindIn(this)`, поиск по цепочке родителей.

Из этого само собой выходит переиспользование: `SettingsPage` и `PausePage` — такие же сцены,
поэтому их можно открыть и как страницу меню, и поверх боя. `SettingsPage` при закрытии сам
разбирается, где он: внутри меню — возврат по стеку, иначе — `QueueFree`.

## 4. Клиент-серверный контракт

### 4.1 Вход в матч

```
ГОСТЬ                                 ХОСТ (MatchHost)
   │                                     │  создал лобби Steam, разослал приглашения
   │  ── подключение по SteamID хоста ──▶│
   │  Join(steamId)                      │  identity берётся из Steam, пароли не нужны
   ├────────────────────────────────────▶│
   │  ◀── LobbyState(игроки, настройки) ─┤
   │                                     │
   │                                     │  StartMatch: генерация мира
   │                                     │  (единственный Rng, сид назначает хост)
   │                                     │
   │  ◀── MatchStart(worldMeta, teamId) ─┤  размеры, сид, теги, хеш мира
   │                                     │
   │  ◀── WorldChunk × N ────────────────┤  карта, порциями (§4.2)
   │                                     │
   │  Ready ────────────────────────────▶│
   │                                     │
   │  ◀── TurnBegin(turn, deadline) ─────┤  матч пошёл
```

Identity приходит из Steam: `SteamID` — это и есть игрок. Ни регистрации, ни паролей,
ни сервера аутентификации. Проверка владения игрой тоже бесплатная — в лобби Steam чужих нет.

`worldMeta` содержит хеш мира. Клиент кэширует карту на диске по этому хешу — переподключение
и реванш на той же карте не стоят ничего.

### 4.2 Стриминг карты — открытый вопрос

Раздаёт карту хост, и это меняет арифметику: домашний аплинк вместо датацентрового, да ещё
и делённый на пятнадцать получателей.

Сжатие делают два приёма. Квантование высоты в `ushort`: диапазон 0..10 000 на 65 536
уровней даёт шаг 0.15 мировой единицы при расстоянии между точками 100 — точность заведомо
избыточная. И дельта-кодирование по строкам плюс общий компрессор: рельеф гладкий, биомы
идут крупными однородными пятнами, коэффициент ~0.12 реалистичен.

**Вариант 1 — хост шлёт карту высот целиком:**

| Мир | Сжатое | × 15 пиров | 10 Мбит | 20 Мбит | 50 Мбит | 100 Мбит |
|---|---|---|---|---|---|---|
| Tiny | 0.1 МБ | 2 МБ | 2 c | 1 c | 0 c | 0 c |
| Small | 0.9 МБ | 13 МБ | 11 c | 5 c | 2 c | 1 c |
| Standard | 3.6 МБ | 54 МБ | 43 c | 21 c | 9 c | 4 c |
| Large | 8.0 МБ | 121 МБ | 97 c | 48 c | 19 c | 10 c |
| Huge | 14.3 МБ | 215 МБ | **172 c** | **86 c** | 34 c | 17 c |

**Вариант 2 — гибрид:** хост шлёт сид и теги, клиенты строят рельеф сами; хост отдаёт только
**авторитетную сетку тайлов** — всё, от чего зависит геймплей.

| Мир | Тайлов | Сжатое | × 15 | 20 Мбит |
|---|---|---|---|---|
| Standard | 62 500 | 0.06 МБ | 0.9 МБ | 0.4 c |
| Large | 140 625 | 0.13 МБ | 2.0 МБ | 0.8 c |
| Huge | 250 000 | 0.24 МБ | 3.6 МБ | **1.4 c** |

Разница на Huge — полторы минуты против полутора секунд.

Ключ к тому, почему гибрид безопасен: рельеф, который клиент сгенерировал сам, используется
**только для отрисовки**. Всё, что решает правила — проходимость, укрытия, стоимость
движения, — приходит из тайлов, а тайлы считает хост. Если у клиента холм на полметра ниже,
это не влияет ни на что, кроме силуэта на экране.

Цена гибрида: код генерации нужен и на клиенте (он и так там есть — дебаг-UI из задачи 1.14),
плюс возвращается требование к `Rng` быть зафиксированным (задача 0.2, она и так в плане),
плюс `MathF.Exp` из §9 переходит из «стоит починить» в «надо починить».

**Решение отложено.** До Standard включительно оба варианта приемлемы, а Large и Huge — это
не завтрашняя задача. Начинаем с варианта 1, потому что он проще; если большие миры окажутся
востребованы, гибрид добавляется сверху без ломки протокола.

Порядок отдачи в любом случае — от стартового города игрока наружу. Матч начинается, когда
доехала окрестность старта, остальное дотекает фоном.

### 4.3 Хост ушёл

Главная плата за listen-server. Матч на 16 человек может идти час, и всё это время он висит
на одном компьютере.

Полноценная миграция хоста — это передача всего состояния новому хосту и переподключение
всех пиров; делать её сейчас несоразмерно дорого. Дешёвый путь: **состояние матча и так
обязано сериализоваться** — для снапшотов, реплеев и кэша. Значит «сохранить и продолжить
позже» получается почти бесплатно. Хост отвалился — все получают файл сохранения, кто-то
поднимает лобби заново.

Отдельно нужен корректный сценарий отвала **гостя**: таймаут, пропуск хода, передача
управления ИИ или сдача. Без этого один упавший игрок вешает матч для остальных.

### 4.4 Ход

```
КЛИЕНТ                                ХОСТ
   │  Command(MoveUnit, PlayCard, …)     │  валидация: право, ресурсы,
   ├────────────────────────────────────▶│  досягаемость, фаза
   │  ◀── CommandAck / CommandRejected ──┤
   │                                     │
   │  EndTurn ──────────────────────────▶│
   │                                     │  все готовы или дедлайн
   │                                     │  → RESOLVE (здесь Rng)
   │                                     │
   │  ◀── TurnResult(события, дельты) ───┤  отфильтровано по видимости
   │  ◀── TurnBegin(turn+1, deadline) ───┤
```

`TurnResult` — список событий, а не полное состояние. Клиент проигрывает их анимациями.
Раз в N ходов хост шлёт `StateSync` с хешем своего состояния; клиент сверяет и при
расхождении запрашивает полную пересинхронизацию. Это страховка от багов в применении дельт,
а не от читов.

### 4.5 Транспорт и Steam

`ITransport` прячет канал. Две реализации: `LocalTransport` (хост говорит сам с собой через
пару потокобезопасных очередей) и `SteamTransport` (`SteamNetworkingSockets`, P2P через
релей SDR).

Что Steam закрывает бесплатно:

* **Identity** — `SteamID` есть готовый идентификатор игрока. Ни аккаунтов, ни паролей.
* **Владение игрой** — в лобби Steam посторонних нет по определению.
* **NAT traversal** — релей SDR решает проброс портов. Хост за домашним роутером просто работает.
* **Лобби и приглашения** — `ISteamMatchmaking`, оверлей, «пригласить друга» из списка Steam.
  Всё это писать самому — недели работы.

Обёртка: **Steamworks.NET** или **Facepunch.Steamworks** — обе чистый C#, живут в процессе
Godot без GDExtension. `GodotSteam` не подходит: он завязан на движок, а `Server` про Godot
знать не должен. На время разработки — AppID 480 (Spacewar).

Честная оценка того, что мы теряем по сравнению с выделенным сервером: **хост может
жульничать.** Он видит весь `MatchState`, включая чужие руки и невскрытые паки. Против
остальных пятнадцати защита полная — они получают только отфильтрованные по видимости
данные, — но хост привилегирован, и с этим ничего не сделать в рамках listen-server.

Для игры в лобби с друзьями это норма — так устроено большинство кооперативов и немалая
часть PvP-игр. Если когда-нибудь понадобится рейтинговый режим без доверия к хосту, `Server`
остаётся библиотекой без Godot, и выделенный вариант достраивается `Exe`-обёрткой плюс
валидацией Steam-тикетов. Дверь не заперта, просто сейчас в неё не идём.

## 5. Генерация мира: теги → STEP

Пайплайн живёт в `Core/Generation`, гоняет его сервер. На клиенте тот же код доступен только
для дебаг-превью миров (задача 1.14) — на геймплей он не влияет.

```
WorldSeed ─┐
Tags ──────┼──▶ Planner ──▶ Step[] ──▶ Executor ──▶ WorldLayers ──▶ TileMap ──▶ WorldState
Size ──────┘                   │                        │
							   │                        └─ Height, Water, Temp,
							   │                           Rock, Biome, Resource,
							   │                           Fertility, Name
							   └─ каждому шагу: Rng(Hash(seed, stepIndex))
```

Сейчас `World.Generate()` захардкожен на три `RadialPrimitive` и полностью игнорирует
`Configuration.ShapeFeature` — это главный пробел.

### 5.1 Теги

Тег — декларация намерения («мир-архипелаг», «с вулканом», «холодный»), а не рецепт.
Категории уже описаны в `Features.cs`: Size, Shape, Terrain, Water, Climate, Resource,
Landmark, Civilization.

Что нужно доработать:

* **Симметричность `Excludes`.** Сейчас `IslandFeature` исключает `AtollFeature`, а обратного
  нет. Правильно — не хранить `Excludes` в каждом теге, а вычислять конфликты из одного места:
  теги внутри группы взаимоисключающие по умолчанию, плюс явная таблица кросс-групповых
  конфликтов (`Desert` × `Rainforest`).
* **Requires / Implies.** `RiverDelta` требует `River`. `Atoll` подразумевает `CoralReef`.
* **Вес и бюджет.** У тега — стоимость; `MaxTotalFeatures` тратится как бюджет, а не как счётчик.
* `Excludes` не должен аллоцировать `HashSet` при каждом обращении — сделать `static readonly`.

### 5.2 Planner

Чистая функция `(Tags, Size, Seed) → Step[]`:

1. валидирует набор тегов (конфликты, requires), при неполноте — доращивает случайными
   совместимыми тегами до бюджета;
2. раскрывает каждый тег в шаги через `ITagExpander`;
3. сортирует шаги по фазам (порядок фаз фиксирован):

| Фаза | Что делает | Примеры шагов |
|---|---|---|
| `Base` | грубая форма суши | `ContinentMass`, `IslandCluster`, `AtollRing` |
| `Tectonic` | горы, разломы, плато | `MountainRange`, `Rift`, `Plateau`, `Volcano` |
| `Noise` | детализация, domain warp | `FbmDetail`, `Warp` |
| `Erosion` | гидравлическая + термическая | `HydraulicErosion`, `Talus` |
| `Hydrology` | стоки, реки, озёра, дельты | `FlowAccumulation`, `CarveRivers`, `FillLakes` |
| `Climate` | температура, влажность, ветра | `Latitude`, `Orographic`, `Moisture` |
| `Biome` | классификация по (T, W, H, slope) | `ClassifyBiomes` |
| `Resource` | руды, плодородие, лес | `ScatterOres`, `Fertility` |
| `Landmark` | руины, кристаллы, священные горы | `PlaceLandmarks` |
| `Gameplay` | тайлы, старты команд, проходимость | `BakeTiles`, `PlaceStarts` |
| `Post` | имена, нормализация, кэши | `NameFeatures`, `BuildIndex` |

Планировщик отдельно от исполнителя даёт две вещи бесплатно: план можно показать в дебаг-UI
и залогировать вместе с матчем.

### 5.3 Step и контекст

```csharp
public abstract class Step
{
	public abstract StepPhase Phase { get; }
	public abstract void Execute(StepContext context);
}

public sealed class StepContext
{
	public Rng Rng;                    // свой инстанс на шаг, не глобальный статик
	public WorldLayers Layers;
	public WorldConfiguration Config;
}
```

Сейчас `Step.Execute(Grid<float> grid)` слишком узко: эрозии нужен доступ к нескольким слоям
сразу, размещению стартов — к тайлам и биомам.

### 5.4 Слои

`float[]` на каждый слой не годится: Huge = 25 млн точек = 100 МБ на слой, шесть слоёв — 600 МБ.

* `Height` — `float` (нужна точность для рельефа и разрушений);
* `Temperature`, `Moisture`, `Fertility` — `byte`;
* `Biome`, `Rock`, `Resource` — `byte` (перечисления);

Итого ~150 МБ на Huge вместо 600. `Grid<T>` уже generic — это вопрос типов, а не переписывания.

### 5.5 Тайлы

```
TILE_POINTS = 10  →  1 тайл = 10×10 точек = 1000×1000 мировых единиц
Tiny   (500×500 точек)   =  50×50  тайлов
Huge   (5000×5000 точек) = 500×500 тайлов = 250 000 клеток
```

Тайл агрегирует точки: средняя высота, доминирующий биом, макс. уклон, проходимость, наличие
воды. Пересчитывается только при разрушении рельефа в его пределах. `TILE_POINTS = 10` делит
`PointCountPerChunkSide = 50` нацело — границы тайлов не режут чанки.

## 6. Команды (фракции) и стартовые города

```
Team ──1:1──▶ StartCity ──▶ прочие City
  │
  ├── Deck (карты)
  ├── Resources
  ├── Vision (туман войны — считается на сервере)
  └── Units[]
```

### Размещение стартов — шаг фазы `Gameplay`

1. **Скоринг кандидатов.** Для каждого тайла — доля проходимой суши в радиусе R, доступ
   к пресной воде, ресурсы поблизости, удалённость от края мира.
2. **Отбор с минимальной дистанцией.** Poisson-disk по отобранным кандидатам,
   `minDistance = f(worldSize, teamCount)`.
3. **Проверка честности.** Дисперсия скоров не больше порога; иначе откат и повтор с другим
   сидом ветки (не всего мира). Максимум N попыток, дальше — ослабление порога.
4. **Связность.** Все старты достижимы друг от друга (BFS по проходимым тайлам) — либо явно
   помечено, что мир островной и нужен транспорт.

`MaxFactionCount` в `Features.cs` доходит до 32 у `HugeSizeFeature`, при заявленных 16 —
привести в соответствие.

### Город

Город — не юнит: сущность на тайле с зоной влияния (радиус в тайлах), очередью производства,
складом и списком построек. Стартовый отличается флагом `IsCapital` и набором построек.

## 7. Система карт

```
CardDefinition (данные, Data/Cards/*.json)
	  │  id, name, rarity, cost, type: Unit | Magic, effects[], mythicCondition
	  ▼
CardInstance (в коллекции игрока, живёт на сервере)
	  │  definitionId, isMythic, mythicProgress
	  ▼
Deck  ──shuffle(Rng сервера)──▶ DrawPile ──draw──▶ Hand ──PlayCard──▶ Resolver
								   ▲                                     │
								   └─────────── DiscardPile ◀────────────┘
```

* **Юнит-карта** создаёт `Unit` на тайле; проверки — зона призыва, проходимость, стоимость.
* **Магия** исполняется стек-машиной эффектов (`ISymbolOp` / `SpellInterpreter`). Каждый оп
  детерминирован и получает `Rng` из контекста команды.
* **Паки.** `PackTable` — веса редкостей + pity-счётчик. Вскрытие целиком на сервере: клиент
  шлёт `OpenPack`, получает результат. Содержимое невскрытого пака на клиенте не существует —
  вскрыть его локально или подсмотреть нечем. Это главный практический выигрыш от смены
  архитектуры.
* **Mythic.** Условие апгрейда — предикат над состоянием матча («убить 10 юнитов», «пережить
  5 ходов в осаде»). Проверяется в фазе `Upkeep`, порождает событие.

Ключевое ограничение: **эффект карты не мутирует состояние напрямую**, а возвращает список
операций, которые применяет резолвер. Только так эффекты остаются тестируемыми.

## 8. Ход и разрешение

```
┌──────────┐   таймер / все готовы   ┌──────────┐    сервер, здесь Rng   ┌──────────┐
│  PLAN    │────────────────────────▶│  LOCK    │──────────────────────▶│ RESOLVE  │
│ клиенты  │                         │ команды  │                       │ по фазам │
│ шлют     │◀────────────────────────│ собраны  │                       │ магия,   │
│ команды  │      следующий ход      │          │                       │ движение,│
└──────────┘                         └──────────┘                       │ бой      │
																		└────┬─────┘
																 ┌───────────▼──────┐
																 │   UPKEEP         │
																 │ доход, добор,    │
																 │ паки, погода     │
																 └───────────┬──────┘
																			 │
														TurnResult, отфильтрованный
														по видимости каждой команды
```

Порядок разрешения внутри `RESOLVE` фиксирован: магия до движения → движение → столкновения →
бой → разрушения рельефа → эффекты конца хода. Конфликты (двое в одну клетку) решаются по
детерминированному ключу: инициатива → приоритет команды → `Hash(turn, unitId)`. Никаких
«кто раньше нажал» — иначе исход зависел бы от пинга.

Валидация команд на сервере — не формальность, а единственная защита. Клиент может прислать
что угодно; сервер проверяет право хода, фазу, ресурсы, досягаемость и владение картой.

## 9. Детерминизм и случайность — что изменилось

Смена архитектуры сняла самое жёсткое требование. Раньше нужно было, чтобы шестнадцать машин
на разных ОС и процессорах прошли миллионы операций с плавающей точкой и получили побитово
одинаковый результат. Теперь симуляция крутится в одном процессе, и это требование исчезло
целиком.

Что осталось — и почему `Rng` всё же стоит написать:

| Зачем | Насколько важно |
|---|---|
| **Воспроизведение мира по сиду** — баг на Linux-сервере повторить на Windows-машине разработчика | Высоко. Рабочий процесс, а не теория |
| **`Fork(salt)` для параллельной генерации** — сид на чанк `Hash(seed, x, y)`, результат не зависит от порядка потоков | Высоко. Без этого генерацию не распараллелить |
| **Снапшот состояния генератора** — сейв матча и реплей | Средне. Из `System.Random` состояние не достать |
| **Равномерный `RangeInt`** — раздача редкостей в паках | Средне. Штатная реализация смещена на больших диапазонах |
| Согласие клиентов между собой | **Не требуется** — если только не выберем гибрид из §4.2, тогда рельеф придётся воспроизводить на клиенте |

Про `System.Random`, раз уж вопрос поднимался: конструктор без сида действительно использует
xoshiro256\*\*, но **конструктор с сидом — нет**. Комментарий в исходниках рантайма прямой:
без сида «we can implement this however we like», с сидом «we still need to respect the same
algorithm that's been used in the past». То есть `new Random(seed)` уходит на legacy-путь —
вычитающий генератор Кнута. Документация при этом не гарантирует стабильность
последовательности между версиями .NET.

**Решение (24.08.2026): движок оставлен прежним — `System.Random`.** Аргументы за свой PRNG
после отказа от lockstep стали мелкими, а цена замены в будущем — один файл: `Core/Utils/Rand.cs`
не отдаёт наружу ничего, кроме шести методов. Структурная часть при этом сделана: `Rand` —
экземпляр, а не статик, и приходит в шаг через `StepContext`.

Что придётся вернуться и доделать, если понадобится:

* `Fork(salt)` — производный генератор с сидом `Hash(seed, chunkX, chunkY)`. Нужен, когда
  генерацию начнём распараллеливать по чанкам: иначе результат зависит от порядка потоков.
* Снапшот состояния генератора — для сейва матча. Из `System.Random` состояние не достать,
  так что этот пункт и есть главный кандидат на замену движка.
* Гибридный стриминг карты из §4.2 — он требует, чтобы клиент воспроизвёл рельеф хоста,
  и тогда стабильность последовательности между версиями .NET снова станет обязательной.

Отдельно про `MathF.Exp` в `Primitive.EvaluateFalloff` (ветка `FalloffType.Gaussian`).
У IEEE 754 нет требования корректного округления для `exp`, и .NET уходит в C-рантайм
платформы — msvcrt на Windows, glibc на Linux. Значит один и тот же сид даст чуть разный
мир на машине разработчика и на сервере. Для геймплея это ничего не ломает (мир-то один,
серверный), но ломает воспроизведение багов. `MathF.Sqrt` безопасен — для него корректное
округление обязательно. Лечится полиномиальной аппроксимацией на `+` и `*`. Приоритет —
средний: `Gaussian` сейчас нигде не используется.

Что уходит из старого плана как более ненужное: побитовая согласованность клиентов, сверка
хешей между клиентами каждый ход, запрет на `Parallel.For` в симуляции.

Что остаётся из старых замечаний по коду:

| Проблема | Где | Почему важно |
|---|---|---|
| ~~Глобальный статик `Rand`~~ | — | Исправлено в 0.2/0.3: экземпляр приходит через `StepContext` |
| ~~Нет проверки отрицательных индексов~~ | — | Исправлено в 0.3 вместе с переездом `Grid` |
| ~~`path[i-1]` при `i=0` в `LinePrimitive`~~ | — | Исправлено: `GetPathDirection` обрабатывает путь из одной точки |
| `Seed = (int)GD.Randi()` в клиенте | `World._Ready()` | Сид назначает хост (этап 2) |
| `TracePathByValue` — заглушка | `Core/World/Grid.cs` | Возвращает одну точку; режим `ByValue` непригоден до задачи 1.8 |
| `Configuration.ShapeFeature` не используется | `World.Generate()` | Теги ни на что не влияют |

Про статик стоит пояснить: раньше он мешал детерминизму, теперь мешает сильнее. У хоста
`MatchHost` крутится на своём потоке, а клиентский код — на главном; общий статический
генератор превращается в гонку данных при первом же параллельном обращении. Это не
рассинхрон, а плавающий неотлаживаемый баг.

## 13. Приложение A — сборка

Один проект, `net8.0`, без мобильного экспорта.

```xml
<Project Sdk="Godot.NET.Sdk/4.6.1">
	<PropertyGroup>
		<TargetFramework>net8.0</TargetFramework>
		<EnableDynamicLoading>true</EnableDynamicLoading>
		<LangVersion>12</LangVersion>
	</PropertyGroup>

	<PropertyGroup>
		<Nullable>annotations</Nullable>
	</PropertyGroup>

	<PropertyGroup>
		<WarningsAsErrors>CS0219</WarningsAsErrors>
	</PropertyGroup>
</Project>
```

`Nullable = annotations` разрешает синтаксис `Type?` и `[MaybeNullWhen]`, но не включает поток
nullable-предупреждений: на полном `enable` Godot-код завалило бы ими.

`WarningsAsErrors = CS0219` ловит присвоенную, но не прочитанную переменную. Именно этот варнинг
молча пропустил баг с `SizeFeature` в раннем ревью.

`Godot.NET.Sdk` компилирует все `.cs` в папке проекта — при одной сборке это ровно то, что нужно,
и `Compile Remove` больше не требуется.

**Steam.** Пакет ставится командой `dotnet add package Steamworks.NET` — версию не фиксируем
руками, пусть подтянется актуальная. Рядом с `project.godot` должны лежать `steam_api64.dll`
из Steamworks SDK и `steam_appid.txt` с идентификатором приложения (на время разработки — 480,
Spacewar). Оба файла в `.gitignore`: бинарник SDK в репозиторий не кладут, а `steam_appid.txt`
в релизной сборке не нужен вовсе — там идентификатор приходит от самого Steam.

Альтернатива, если возиться с нативной библиотекой не хочется: пакет `Steamworks.NET.AnyCPU`
несёт бинарники внутри себя.

## 13.1 Стиль кода

Дополнение к правилам из настроек проекта.

**Комментариев в коде нет.** Ни поясняющих, ни XML-документации, ни `TODO`. Если что-то нужно
объяснить — это идёт в диалог или в этот документ, но не в файл. Регионы `#region` остаются:
это структура, а не комментарий.

Отсюда следствие: всё, что раньше жило бы в `TODO`, живёт в §10 «Прочий техдолг» и в дорожной
карте. Иначе оно просто потеряется.
